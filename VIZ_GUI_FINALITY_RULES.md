# Visualizing Crosslink's finality rules

Two things live here: the test-format scenes that reproduce
[`FINALITY_DIAGRAM.html`](./FINALITY_DIAGRAM.html) in the GUI, and the list of places where
the GUI's own finality operators do not yet compute what
[`FINALITY.md`](./crosslink_book/src/FINALITY.md) defines. The second list is deferred work: nothing in it is
fixed, and the scenes were built so that they can be looked at without it.

## 1. The scenes

Three `.zeccltf` files in `zebra-crosslink/crosslink-test-data/`, generated by
`crosslink_write_finality_diagram_scenes` in `zebra-crosslink/zebrad/tests/crosslink.rs`:

| file | diagram section | what it shows |
|---|---|---|
| `finality_diagram_1_candidate.zeccltf` | §1, §2, and §3 "before" | one PoW chain of ten blocks, three BFT blocks over sliding σ-windows, marker on P5 |
| `finality_diagram_2_benign_reorg.zeccltf` | §3 "after" | the same, then a longer branch off P8 citing an older BFT block; the best chain moves, the marker does not |
| `finality_diagram_3_conflicting_fork.zeccltf` | §4 | the same BFT chain, and a heavier branch forking from P3, *below* the marker |

### Viewing them

In the GUI, press <kbd>F3</kbd> for the debug panel, put the path in the **Test Format**
box, and press one of:

- **View (no consensus)** — the picture is built from the file's own blocks and the node is
  not consulted at all. This is the only way to see scene 3.
- **Load into zebra** — the file's blocks go through the real admission path, exactly as
  before. Works for scenes 1 and 2.
- **Back to live chain** — leaves view mode.

While a file is being viewed the other two buttons do nothing but say so in the log: the
node's chains are not what is on screen. Go back to the live chain first.

Switching between the two sources clears the screen first: they describe unrelated chains,
and the GUI keys blocks by hash, so merging them would interleave two pictures.

The view path is `VizScene` in `zebra-crosslink/zebra-crosslink/src/viz2.rs`. It reads the
file's `LOAD_POW` and `LOAD_POS` instructions, indexes the blocks against each other,
picks the heaviest chain the way fork choice would, and derives the finalized marker the
way this node derives it. It draws every load instruction, `SHOULD_FAIL` ones included:
that flag says what the node does with a block, not whether the block can be drawn.
`viz2::scene_tests` checks each scene file against the picture it produces.

### Scene 3 needs the view path

This node will not hold scene 3. The commit that advances `fin` discards every non-finalized
chain that does not contain it, Zebra rejects blocks that fork below its finalized tip, and
`read::sidechain_forks` — the only path that serves whole blocks off the best chain, the
others being peer claims and the headers carried inside BFT blocks — reads the
non-finalized state alone, so a branch below the finalized block could not be served even
if it had been admitted. Loading the scene into the node instead demonstrates the refusal,
which is what `crosslink_finality_diagram_3_conflicting_fork_is_refused` asserts: all six
branch blocks are rejected, the best chain stays at P8, and P5 stays finalized.

That refusal is sticky fork choice (FINALITY.md §4.3), not something CL2 requires. The
picture is what the construction permits; the refusal is what this tree does.

### Where the scenes differ from the drawing

Three of the drawing's details cannot be built as drawn.

- **`P10.context_bft = S6` with `S6` covering P8–P10 is impossible.** The fat pointer is
  inside the hashed part of the header, so a BFT block cannot carry the header of a PoW
  block that points at it. Each scene interleaves the two chains instead: a BFT block only
  covers PoW blocks that already exist, and a PoW block only cites a BFT block that
  already exists.
- **There is no `LF` lag.** The drawing has `LF(P10) = S4` while P10 cites S6, so `fin`
  sits two BFT blocks behind the tip's context. Every stored bft-block is already decided,
  so `bft-last-final` is the identity here (FINALITY.md §3.1). The scenes therefore stop the BFT chain at the block whose
  snapshot, `parent(headers_bc[0])`, is the block the diagram labels `fin`, so the marker the
  GUI draws lands where the diagram writes it. Matching the drawn arrows and matching the
  drawn marker are different files; these match the marker.
- **Regtest difficulty is constant**, so a branch can only win by length. The drawing
  replaces P8–P10 with three higher-work Q blocks; scene 2 replaces P9–P10 with three blocks,
  Q9–Q11, instead. The point is unchanged: the new best chain still contains `fin`.

## 2. Deferred: the F8 operators

<kbd>F8</kbd> cycles `InteractiveVizOp` (`zebra-gui/src/lib.rs`) through
`LF → bft_last_final → snapshot → candidate → tip`, and hovering a block highlights that
operator's result (`apply_viz_op` in `zebra-gui/src/viz_gui.rs`).

`tip` and `snapshot` are correct. `proving_blocks` carries all `σ` of a BFT block's
`headers_bc`, so `proving_blocks.last()` is the tail of the bc-chain the block confirms, and
`points_at_bc_block` is `BftBlock::snapshot_hash`, i.e. `parent(headers_bc[0])`. The rest
have open problems.

### 2.1 `candidate` prunes from the wrong block

`candidate(H) := lca(snapshot(LF(H)), prune_σ(H))`. The operator computes the second
operand as `bc_at_h(state, bc_tip_height − σ)`, which is `prune_σ(bc_best_tip)`. That
agrees with the definition only when the hovered block *is* the tip. Every case the
diagrams exist to show — a candidate derived from a block below the tip, or from a block
on a branch — gets the wrong operand.

It should walk the hovered block's own parent links σ times.

### 2.2 `bft_last_final` is a placeholder

The operator returns `bft.parent_hash`: a lag of exactly one BFT block. Three answers are
in play and none of them agree:

- what this tree computes: the identity, since every stored BFT block is decided;
- what the operator returns: the parent;
- what the diagram draws: two blocks back.

Deciding this decides what `LF` means in the GUI, since `LF` is
`points_at_bft_block` followed by `bft_last_final`. If the honest answer is the identity,
the general case still deserves a way to be shown — a configurable lag would let one scene
demonstrate both.

### 2.3 σ is hardcoded

`apply_viz_op` uses `const TMP_SIGMA: u64 = 3`. It happens to equal
`PROTOTYPE_PARAMETERS.bc_confirmation_depth_sigma`, so nothing is wrong today, but the
parameters already reach `service_viz_requests` and should reach the GUI.

### 2.4 `fin` is missing

`fin` is in the enum, commented out. It is not a function of a block: it is node-local
monotone memory updated from `candidate(bc_best)` on each best-chain change
(FINALITY.md §3.2), so an operator can only surface the value the node already sends. That
value is `bc_finalized_tip_height`, which `viz2.rs` fills from `new_network::fin::fin()`,
so the operator has only to highlight the block at that height.

### 2.5 `origbft_last_final` is `todo!()`

`cycle_next` never reaches it, so F8 cannot panic on it today. It is reachable if the
cycle order ever changes.
